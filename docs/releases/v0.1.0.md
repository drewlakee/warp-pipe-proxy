# Warp Pipe Proxy v0.1.0

First tagged release of the VLESS Reality proxy installer. The supported release environment is **Ubuntu 24.04 LTS, amd64 (x86_64), systemd, sing-box 1.14.4**. Traffic exits through the server's public IP address.

This release combines per-device access, automatic firewall inspection, revocation that cannot be undone by an external reachability failure, and permanent removal of project data. It also introduces an explicit project version and an exact lock for direct APT dependencies.

## Install this release

Use a fresh Ubuntu 24.04 amd64 VPS with root or sudo access and a public IPv4 address. Allow incoming TCP 10443 in the provider firewall. The server needs access to APT repositories, HTTPS and DNS.

```bash
git clone https://github.com/drewlakee/warp-pipe-proxy.git
cd warp-pipe-proxy
git checkout v0.1.0
./warp-pipe-proxy.sh --version
sudo ./warp-pipe-proxy.sh install
warp-pipe-proxy --version
sudo warp-pipe-proxy device-add --device phone
sudo warp-pipe-proxy client-qr --device phone
```

Both version commands print `warp-pipe-proxy 0.1.0`. The first reads the checkout; the second reads the installed copy. Version inspection does not require sudo.

A new installation has no client devices until one is added. QR codes, links and exported profiles contain access credentials. The JSON client profile includes DNS and TUN settings; a VLESS URI alone does not include those settings.

For an existing checkout, run `git fetch --tags origin`, select `v0.1.0` and invoke `sudo ./warp-pipe-proxy.sh install` from that checkout. Reinstallation preserves the current device credentials. `sudo warp-pipe-proxy install` reapplies the already installed version; it does not fetch a new release. There is no automatic update command in v0.1.0.

| `fail2ban` | `1.0.2-3ubuntu0.1` | VPS mode |

Installation requests exact `package=version` specifications. It can install missing system dependencies and upgrade older ones to the lock. If an applicable installed package is newer, preflight refuses before APT or service configuration changes; there is no automatic downgrade. Unavailable pinned packages cause an error rather than a silent version substitution.

An existing sing-box must already be the expected package and runtime version. A different version, a manually installed binary or a `PATH` entry shadowing the packaged binary is rejected before APT or configuration changes. The installer does not upgrade or downgrade an existing engine automatically. After installation, `check` verifies the locked environment as well as the proxy.

This is a lock for direct project dependencies. It does not pin the entire OS image, kernel or transitive dependencies, and the `python3` pin is the Ubuntu metapackage version. CI publishes the complete guest package inventory to describe the tested OS environment. No `apt-mark hold` or global APT preferences are added; normal OS update policy remains under the administrator's control.

`VERSION`, `dependencies.lock.json` and their `release.py` validator are copied into `/usr/local/lib/warp-pipe-proxy/` with the installed command. They contain no credentials and introduce no additional state under `/etc/warp-pipe-proxy/`.

## Firewall inspection is automatic

An active UFW keeps all its rules and policies, including restrictions on which source IPs may reach SSH. Add a proxy allowance to that existing policy yourself if one is needed. Local proxy checks cannot establish external reachability through every provider or host firewall.

When no firewall policy exists, the installer discovers SSH ports, checks other listeners, permits SSH and the proxy, and enables UFW with other incoming traffic denied. It recognizes the supported system DHCP clients. Disabled UFW with saved user rules, or another iptables/nftables policy, causes a refusal before configuration is applied. No additional firewall option is required.

## Device access and revocation

Each named device has its own UUID. The installer can export a VLESS link, terminal QR code or sing-box JSON profile for that explicit device. Key rotation replaces the shared Reality key pair and short ID plus every active device UUID; names and revoked status remain.

`device-revoke` commits the change after local validation and application. A subsequent external HTTPS probe is diagnostic: a failing site or network path cannot roll credentials back and restore access to that device. Other active devices keep their profiles. If the service was stopped, revocation does not start it.

A failure while applying credentials, configuration or service state leaves the proxy stopped with autostart disabled. The validated intended credentials and pending marker allow completion without reverting to old access. Further device changes and installation with obsolete credentials are blocked until the pending revocation is completed. Complete `uninstall` remains available.

Ordinary installation, device addition and key rotation retain their health checks and configuration rollback behavior. Private destination addresses remain blocked by default, including addresses obtained by resolving a hostname; administrators can configure explicit shared subnet exceptions.

## Permanent uninstall

```bash
sudo warp-pipe-proxy uninstall
```

Removal verifies ownership, stops and disables the proxy, then deletes its settings, credentials, exported compatibility profiles, installed command and modules, service files, working directory, all old installer backups and installer logs. It creates no new backup or uninstall log. Proven project-owned Unbound, fail2ban, BBR and APT source files are removed as well.

Only identifiable UFW proxy allowances in their original form with the exact `warp-pipe-proxy Reality` comment are removed. Administrator rules, SSH rules and current UFW policies remain; allowances now serving SSH are preserved. Shared system packages, the service account, generic repository key and shared Unbound/fail2ban data remain. Existing BBR kernel settings persist until reboot or an explicit administrator change, and entries in the shared system journal are not individually purged.

Interrupted deletion can be resumed from the source checkout. A temporary `/var/lib/warp-pipe-proxy-uninstalling.json` marker contains ownership and cleanup information without keys or profiles; it is deleted on success. A fresh installation creates new keys and an empty device registry, so old exported profiles no longer work. Shared administrator configuration may need review, and an active UFW continues to require an appropriate proxy allowance.

## Validation scope

The [Proxy checks workflow](https://github.com/drewlakee/warp-pipe-proxy/blob/v0.1.0/.github/workflows/proxy-checks.yml) runs Python unit tests, Bash syntax checks and the [Ubuntu VM scenario](https://github.com/drewlakee/warp-pipe-proxy/blob/v0.1.0/tests/ubuntu-vm.sh). The VM scenario exercises:

- Installation on an empty firewall and externally initiated VLESS HTTPS requests.
- Reinstallation with source-restricted SSH, preservation of the active firewall, and a VM reboot.
- Denial of private IPv4, IPv6 and resolved private destinations, plus an explicit subnet exception.
- Device activity, successful revocation despite an external probe failure, and rollback after an ordinary mandatory check failure.
- Permanent removal of project files, keys, backups and logs while preserving administrator firewall policy and unrelated configuration.
- Repeated removal, fresh installation, rejection of old client profiles and connection using a new device.

The release lock identifies the CI provenance of its exact direct versions. Release validation also records the full VM package inventory as an artifact. The verified target is Ubuntu 24.04 amd64 with systemd; this does not establish support for other Ubuntu releases or architectures. `--container` remains available for Ubuntu 24.04 amd64 with systemd as PID 1 and published ports, but it is not a separately validated full-cycle target for v0.1.0.
